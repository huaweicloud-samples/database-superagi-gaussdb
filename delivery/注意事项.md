# 注意事项（GaussDB 507 适配）

> 运维视角的行为差异与限制清单。适配代码已处理其中大部分；标注"运维注意"的条目需要部署/运维侧自行遵守。

## 1. 密码与连接

- **DB_URL 密码必须 percent-encode**（运维注意）：密码含 `@ : / ? #` 等字符时，写在 `DB_URL` 中必须编码（`@` → `%40`，`:` → `%3A`，`/` → `%2F`，`?` → `%3F`，`#` → `%23`）。**推荐改用分项配置**（DB_HOST / DB_USERNAME / DB_PASSWORD / DB_NAME），密码原样填写、无需编码。
- **alembic 手动执行**：手工跑迁移时需要先设置环境变量 `DB_URL`（`opengauss+psycopg2://...`）和 `ENCRYPTION_KEY`（32 字符），再执行 `alembic upgrade head`。entrypoint.sh 启动路径已自动带齐。
- 连接驱动为开源 psycopg2 2.9.x；sha256-only 认证实例不可直连（见部署文档 2.4 节）。

## 2. A 兼容模式语义差异

GaussDB 的 A（Oracle）兼容模式与 PostgreSQL 存在行为差异，本适配的处理方式如下：

- **空串 `''` 写入一律转 NULL**：这是 A 兼容模式的库端语义。适配已用 Engine 级 `before_cursor_execute` 钩子拦截，将 SQL 参数中的空串改写为单空格 `' '`，且**全局生效**（含 DBSessionMiddleware / Celery 等内部自建 engine 的路径）。
  - 运维注意：应用层判断"空字符串"请用 `IS NULL` 或先 strip 再比较，不要依赖 `= ''` 能命中。
- **VARCHAR(n) 按字节计数**：UTF-8 下中文每字占 3 字节，`VARCHAR(255)` 实际只能存约 85 个汉字。上游 schema 未改，录入长中文文本时注意截断风险。
- **DATE 映射 TIMESTAMP(0)**（`mapping_date_to_datea=on` 下的库端行为）：本适配全部模型的默认值都改在 Python 侧用 `utcnow` 生成，不依赖库端 DATE 语义，对该差异无感。自建表时注意。

## 3. 向量能力

- **metadata 过滤为索引后过滤**（运维注意）：带过滤条件的向量检索，命中数可能少于 `top_k`（GaussDB 向量索引先取近邻、后做过滤的特性）。无过滤场景不受影响。对召回完整性敏感的业务请放宽 top_k 或二次检索。
- **GsDiskANN 磁盘占用与重建**：GsDiskANN 索引约为原始向量数据的 **10–50 倍**磁盘，容量规划时计入。数据量变化超过 **20%** 建议重建索引（DROP 后由惰性建索引机制重建，或手工重建）。
- **余弦距离零向量 NaN**（运维注意）：余弦距离下零向量产生 NaN，避免写入全零 embedding（如 embedding 服务异常返回空值时应丢弃而非落库）。
- **非 sysadmin 不能在 public schema 建函数**：本适配**零 DB 函数依赖**，不受影响；但用户若自行在库上建扩展/函数会遇到权限限制，需 DBA 以 sysadmin 执行或调整权限。
- **向量表结构**（便于排障）：
  - `id VARCHAR(36)` 主键（UUID 字符串）
  - `text TEXT`
  - `metadata JSONB`
  - `embedding floatvector(dim)`
  - **表名即 index_name**，支持连字符（默认 `super-agent-index` / `super-agent-index1` 可直接使用）。

## 4. 分布式形态差异（相对集中式）

本适配在集中式（A 兼容模式）上验证，分布式形态存在以下差异，部署前必读：

- 兼容模式为 `datcompatibility='ORA'`（集中式为 `'A'`），且 `pgxc_node` 非空（分布式判定依据）。
- **向量建表硬限 1024 维**：超过 1024 维的 embedding 模型（如 ada-002 的 1536 维）在分布式形态不可用，建表直接报 `dimensions for type vector cannot exceed 1024`。集中式无此限制（≤4096，>1024 自动走 GsDiskANN+PQ）。
- 34 个迁移的完整 downgrade/upgrade 双向回归是在**集中式**验证的；分布式部署前建议先跑 `delivery/tests` 分层验证（reset_test_db → t1 → t2 → t3 → t4）确认目标环境行为一致。

## 5. 已知限制与设计内回退

- **UI/控制器暂无「创建 GAUSSDB 类型向量库」端点**：知识库功能走 `build_vector_storage` 时，若向量库凭据中没有 `url` 键，会**静默回退到元数据库实例**（同实例建向量表，功能可用）。如需独立向量库实例，通过 `GAUSSDB_VECTOR_DB_URL` 指定。后续可补充向量库注册端点。
- **后续补 GAUSSDB 注册端点时须同步补 `search_res` 键**：`GaussDB.get_matching_text` 目前返回 `{"documents": [...]}`；`knowledge_search.py:57` 消费 `search_result['search_res']`，Pinecone/Qdrant/Weaviate 均返回双键（Redis 后端同样缺此键，属上游既有缺口）。注册端点落地前 knowledge_search 选不到 GAUSSDB 索引，故当前不可达。
- **llama_index 0.6.35 适配已校准**：`NodeWithEmbedding` 为 dataclass（属性访问），已在端到端验收中由真实写入 + `<+>` 检索验证（资源向量路径）。
- **清库提示（重置环境必读）**：openGauss 下执行 `DROP OWNED ... CASCADE` 会**连带删除用户拥有的 public schema**，清库后必须重建 schema 并恢复授权（`GRANT CREATE, USAGE ON SCHEMA public TO <user>`）。`delivery/tests/reset_test_db.py` 已内置正确流程（逐表 DROP，不用 DROP OWNED），重置生产/测试库时参考其做法。

## 6. 遗留问题登记（终审记录，2026-09-21）

以下为交付时登记的已知 Minor 项，均不阻塞功能，留待后续触碰相关代码时顺手处理：

- **`_ensure_schema` 首写竞态**（`gaussdb.py`）：uvicorn + celery 双进程同一时刻首次写入同一向量表时，后提交方 CREATE TABLE 报 duplicate table、该次写入失败，重试即恢复（表+索引同事务原子可见）。与既有 Redis 后端 `create_index` 的竞态同类；根治可用 `CREATE TABLE IF NOT EXISTS`（GaussDB 支持性需验证）。
- **向量连接池额度**（`gaussdb.py:78`）：每实例 `pool_size=5`（+默认 max_overflow 10），实例随调用短命、GC 回收，非无界泄漏；但高峰期并发 agent run 可能挤占 GaussDB 连接数（主库池另占 20+50）。向量查询低频，可考虑池调小到 1-2 或按 index_name 缓存 engine。
- **回滚语义精确化**：适配的空串守卫是 **Engine 类级无条件注册**，因此"回滚到 `postgresql://` 连接原 PG"后空串仍会被改写为单空格。如需完全还原 PG 行为，需 revert 空串守卫相关提交（`b469db7`/`9e83cc4`/`d1e11c9`）或注释注册调用。
- **db.py 日志含密码**（上游既有，非本次引入）：`db.py` 连接成功日志打印完整 URL（含密码），建议后续改为脱敏输出。
- **代码层面 Minor**（详见适配过程记录）：`register_gaussdb_compat` 的 `engine=None` 参数已无实际调用差异（可删参）、模块级 flag 置位在 listen 之前（可后移作保险）、main.py 的 helper import 位置与既有分组不符、5 处迁移 downgrade 修复未加行内注释（理由在 commit message `585827e`）。

## 7. 第三轮扩展扫描发现（t7，2026-09-21）

t7（`delivery/tests/t7_extended_e2e.py`）扫描 Settings/Analytics/Agent 生命周期/定时调度/Knowledge 挂载/边界输入/Models 页。**GaussDB 数据层无新增兼容问题**；以下均为上游产品逻辑缺陷（与 GaussDB 无关，按交付纪律只登记不改）：

- **`GET /models_controller/get_api_keys` 必 500**（Model Providers 页的密钥列表接口）：`/users/add` 时 `ModelsConfig.add_llm_config`（`models_config.py:160`）给每个组织写入 `Local LLM` 行，api_key 为**明文** `"EMPTY"`；而 `fetch_api_keys`（`models_config.py:112`）对**所有**行 `decrypt_data`，Fernet 对明文抛 `InvalidToken` → 500。单查接口 `fetch_api_key` 有 `'Local LLM'` 特判（`models_config.py:133`），列表接口漏了。复现：任意新装环境调该端点即 500。
- **无效 id 详情接口 500 而非 404**：`GET /knowledges/user/get/details/{无效id}`（`knowledges.py:86`，`get_knowledge_from_id` 返回 None 后直接取属性）与 `GET /vector_dbs/db/details/{无效id}`（`vector_dbs.py:35`，同型）均缺 None 守卫，抛 AttributeError → 500。
- **webhook 只能增改、不能真删**：控制器仅 add/edit/get（无 DELETE 端点）；且 `WebHookManager.agent_status_change_callback`（`webhook_manager.py:19`）查询时不过滤 `is_deleted`，软删后仍会继续对已删 webhook 投递。运维上如需停用某个 webhook，应把其 `filters` 清空（`{"status": []}`）才真正失效。
- **webhook 投递体 `event` 文本的 old 状态可能为未解析哨兵值**：状态变更经 SQLAlchemy `set` 事件监听（`worker.py:47`）触发，属性未加载时 `old_val` 是 `LoaderCallableStatus.NO_VALUE`，投递体形如 `"LoaderCallableStatus.NO_VALUE to RUNNING"`（投递本身正常，仅文案失真）。
- **`PUT /v1/agent/{agent_id}` 编辑是"追加"而非"更新"**（`controllers/api/agent.py:239`）：每次编辑向 `agent_configurations` 追加一批新配置行，旧行残留；读取侧按行序覆盖，行为可用但表持续膨胀。该端点还会顺带创建一个 CREATED 占位执行（不运行）。
- **`GET /organisations/get/user/{user_id}` 是 GET 却带 `status_code=201`**（`organisation.py:129`）：body 正确，仅状态码怪癖。

运维注意（环境/操作面）：

- **本地手工起 celery 时若要测试定时调度，须加 `--beat`**：产品部署入口 `entrypoint_celery.sh`/`DockerfileCelery` 已带 `--beat`；本地 `--pool=solo` 手工启动默认无 beat，`agent_schedule` 只落库不触发（beat 周期 5 分钟：`initialize-schedule-agent`）。
- **api_keys 表的 key 为明文 UUID 存储**（上游设计）：加密仅用于 `models_config.api_key`（Fernet，`ENCRYPTION_KEY`）。对外暴露面是 `/api-keys` 响应与鉴权头，库内明文属上游现状，交付时知悉即可。
- **终止一次执行的正确姿势**：`PUT /agentexecutions/update/{execution_id}`，body `{"status": "TERMINATED"}`（GUI 同款路径）。没有专用"停止"端点，也不写终止 feed 行——终止以后续 feed 停止增长 + 状态位呈现；在飞的 step 输出仍会落完。
- **编辑 agent 配置后旧行残留**（同上 `/v1/agent` 项）：运维排查 agent 实际生效配置时，以 `agent_configurations` 中该 key **最大 id** 行为准。
- **celery worker 被硬终止会残留孤儿消息**：本项扫描观察到 redis broker 的 `unacked` 哈希中残留一条旧 `execute_agent` 消息（其目标执行已 TERMINATED，若被消费会立即空转返回，无实害），且伴随新任务消费延迟（一个 `.md` 的 summarize 延迟超过 15 分钟才被消费）。运维上：重启 worker 尽量优雅退出（硬 kill 后的 unacked 消息依赖 redis `visibility_timeout`（默认 1h）恢复重投递）；若怀疑任务积压/卡住，查 `unacked` 哈希与 `celery` 列表长度。
